## 1. О проекте

**Tsugi** (次 — «следующий», «дальше») — веб-приложение для отслеживания аниме: каталог, поиск с фильтрами, личный список и **расписание выхода серий**.

Название отвечает на главный вопрос продукта — что следующее и когда. Прежнее рабочее название — OtakuList.

**Цель проекта:** пет-проект для портфолио. Отсюда следует, что приоритет — не количество фич, а качество исполнения: законченность, читаемый код, типобезопасность, обработка краевых случаев и внятная документация. Лучше пять доведённых до конца экранов, чем пятнадцать наполовину.

**Ключевая фича, отличающая проект от типового каталога:** расписание выхода серий с привязкой к личному списку. Каталог открывают один раз, расписание — каждую неделю.

### Решение по API

**Jikan отменён, выбран AniList GraphQL.** Обоснование (в README вынести отдельным разделом):

- запрос ровно нужных полей, без оверфетча;
- есть `bannerImage` и `coverImage.color` — баннер идёт в блок популярного, цвет обложки в подложки карточек (см. 5.1);
- есть `airingSchedule` — без него ключевая фича невозможна;
- мягче лимиты (у Jikan 3 req/sec, 60/min — поиск с дебаунсом упирается);
- есть OAuth и мутации — задел на синхронизацию личного списка.

Минус: нет русских названий (у Jikan тоже нет). Принимаем.

**Приложение обращается к двум внешним адресам** (замерено 16.08.2026 на экране расписания):

| Хост                 | Что               | Запросов на экран |
| -------------------- | ----------------- | ----------------- |
| `graphql.anilist.co` | API               | 3                 |
| `s4.anilist.co`      | обложки и баннеры | 122               |

Больше внешних обращений нет — `@vicons` и шрифты бандлятся в сборку.

Обрати внимание на пропорцию: почти весь сетевой трафик экрана — это изображения, а не данные. Это главный рычаг, если понадобится ускорить загрузку.

### Решение по типам

Типы GraphQL-ответов **не пишутся руками**. Подключается `@graphql-codegen` со схемой AniList; типы генерируются в `src/api/generated/`. Причина: рукописные типы неизбежно расходятся с запросами, и компилятор об этом не узнает.

**Шкала рейтинга — отдельная палитра (решено 10.09.2026).** Оценка тайтла показывается плашкой с заливкой, и у неё свои шесть токенов, не пересекающиеся с состояниями:

| Токен          | Значение  | Текст на ней                |
| -------------- | --------- | --------------------------- |
| `--score-high` | `#128046` | `--on-score-high` `#F7F5F6` |
| `--score-mid`  | `#6E6E6E` | `--on-score-mid` `#F7F5F6`  |
| `--score-low`  | `#D71D1D` | `--on-score-low` `#F7F5F6`  |

Пороги: высокая от 65, средняя от 50, ниже — низкая (шкала AniList 0–100).

**Почему у шкалы свои токены, а не `--success` и `--error`.** Это разные словари: состояние («вышло», «ошибка») и ступень шкалы. Низкая оценка не ошибка, а средняя — не предупреждение. Отдельные имена позволяют менять шкалу, не трогая состояния.

**Почему значения записаны числами, а не через `var(--success)`.** Алиас следовал бы за темой, а текст на плашке — нет: в тёмной теме `--success` становится светлым `#5DBE8E`, и пара с почти белым текстом давала 2.1 при норме 4.5. Поэтому заливки шкалы одинаковы в обеих темах и в тёмном блоке не переопределяются.

**Почему середина серая, а не жёлтая.** Жёлтый не может нести светлый текст: чтобы дать 4.5 к почти белому, заливка обязана опуститься примерно к 34% светлоты, а жёлтый на такой светлоте выглядит коричневым. Нейтральный серый честнее и не притворяется предупреждением.

Контраст текста к заливке: 4.60, 4.70 и 4.74. Сами плашки к карточке — 5.00–5.14 в светлой теме и 3.02–3.10 в тёмной, то есть в тёмной впритык к порогу 3:1 для нетекстовых элементов. Дальше затемнять заливки нельзя: плашки начнут сливаться с карточкой.

Все значения проверены на контраст к своему фону: цветной текст даёт не меньше 4.5, заливки — не меньше 4.5 со своим `--on-*`. Исключение — `--accent` как крупный текст на тёмном (2.8), поэтому для текста и ссылок существует отдельный `--accent-text`.

**Почему фиолетовый в тёмной теме светлее (28.08.2026).** Naive в тёмной теме кладёт на заливки кнопок **чёрный** текст, а не белый. На прежнем `#7453C1` это давало 3.75 при норме 4.5. Поднятие светлоты до `#9173D9` даёт 5.66 с чёрным текстом и заодно 4.18 к тёмной карточке — прежний вариант не дотягивал даже до 3, из-за чего рамка выбранного дня была едва различима. Тон сохранён точно: 258° в обеих темах, в тёмной выше насыщенность (57 против 47) — приглушённые цвета на тёмном фоне выглядят грязными.

**Почему усиливаем число, а не приглушаем название (30.08.2026).** Внутри кнопки «сегодня» название дня и число должны различаться так же, как в обычные дни, где название приглушённое, а число берёт полный `--text`. Приглушать альфой (`color-mix(--accent 80%, transparent)`) нельзя: альфа подмешивает фон, то есть приглушение и потеря контраста — здесь одно и то же действие, и текст проваливается ниже нормы. Поэтому название остаётся на `--accent-text`, а число получает отдельный токен посильнее.

Значение подобрано так: взяты тон и насыщенность акцента (258°, 47% в светлой и 57% в тёмной), подобрана только светлота. Ровное совпадение с обычными днями давало почти чёрно-фиолетовый, в котором цвет не читался, поэтому взята ступень мягче.

Имя `-strong` означает «контрастнее», а не «темнее»: в тёмной теме этот цвет **светлее** `--accent-text`. Название `-dark` описывало бы только светлую тему и в тёмной врало бы.

**Почему `--on-*` устроены по-разному.** `--on-accent` белый в обеих темах, потому что фиолетовый тёмный при любой светлоте. `--on-success` меняется по темам, потому что зелёный тёмный в светлой теме и светлый в тёмной, и одно значение текста обе темы не тянет. Правило простое: цвет текста на заливке диктует сама заливка, а не привычка.

**Направление hover и pressed выбирается по читаемости, а не по единому правилу.** Для зелёного в светлой теме оба состояния идут темнее базы: если делать нажатие светлее, контраст с `--on-success` падает до 3.34. В тёмной теме, наоборот, оба светлее. Значения для Naive лежат в `constants/themeVariables.ts`.

### Правило акцентов

- **Фиолетовый — действие и навигация:** кнопки, ссылки, активный пункт меню, выбранный день, пометка «в моём списке».
- **Зелёный — положительное состояние:** эпизод вышел, тайтл просмотрен, действие подтверждено.

Одно про то, что можно сделать, другое про то, что уже произошло, — так они не конкурируют за внимание.

**Счётчик релизов зелёным — сознательное исключение.** Количество само по себе не «положительное состояние», это нейтральная величина. Зелёный взят потому, что счётчик говорит о релизах, а зелёный в этом приложении и есть цвет релизного состояния; полоса дней при этом читается заодно с карточками как одна система. Цена — зелёный становится самым частым цветом на экране и слабее выделяет. Если счётчик начнёт спорить с полосами за внимание, ему стоит стать нейтральным.

**Розовый остался без работы.** Он задумывался как «состояние во времени» — выходит сегодня, в эфире, — но эту роль забрал фиолетовый в отсчёте, а «уже вышло» ушло к зелёному. Дважды при разборе цветов ему не нашлось применения. Токены пока объявлены; если третьего захода не случится, их лучше удалить: неиспользуемый цвет в палитре рано или поздно применяют наугад.

### Почему токены, а не переменные SCSS

**Переменные Sass не умеют темы.** `$main-color` подставляется при сборке, и в готовом CSS никакой переменной нет — только конкретный цвет. Поменять его в рантайме невозможно, значит переключить тему на переменных Sass нельзя в принципе.

Отсюда три слоя:

1. **Палитра** — переменные Sass (`$violet-500`, `$violet-300`). Сырые цвета, compile-time, о темах не знают.
2. **Токены** — два блока CSS-переменных: `:root` и `:root[data-theme='dark']`. Здесь роли получают значения из палитры.
3. **Компоненты** — только `var(--surface)`, `var(--text)`. Про палитру не знают и знать не должны.

Компонент говорит «залей меня акцентом», а какой это цвет в текущей теме — решает тема. Без этого разделения темизация превращается в набор точечных переопределений «а в тёмной теме здесь другой цвет».

### Стыковка с Naive UI

Своих цветов недостаточно: у Naive UI собственная тема, и по умолчанию её `primaryColor` зелёный (`#18a058`). Без переопределения половина интерфейса останется зелёной — как сейчас активный пункт меню.

`n-config-provider` в `App.vue` уже есть, не хватает пропа `theme-overrides`:

```ts
import { darkTheme, lightTheme, type GlobalThemeOverrides } from "naive-ui";

const darkOverrides: GlobalThemeOverrides = {
  common: {
    primaryColor: "#7453C1",
    primaryColorHover: "#8261CE",
    primaryColorPressed: "#6544B0",
    primaryColorSuppl: "#7453C1",

    bodyColor: "#1A1A1B",
    cardColor: "#242425",
    textColorBase: "#E2DBDD",
    textColor3: "#9A9496",
    borderColor: "rgba(226,219,221,.14)",
    successColor: "#5DBE8E",
    errorColor: "#E8705F",
    borderRadius: "8px",
  },
};
```

Три грабли:

- **`primaryColorSuppl` обязателен.** Naive использует его для плотных заливок — залитые кнопки, активный переключатель, ползунок. Задашь только `primaryColor` — часть компонентов останется зелёной.
- **Приглушённый текст — не `textColorBase`.** У Naive нумерованные уровни `textColor1…3`, метаданные берут из третьего.
- **Покомпонентные правки** кладутся в ключи с именами компонентов рядом с `common`: `Button`, `Menu`, `Card`. Сначала настраивается `common`, компоненты наследуют.

### Айдентика

**Шрифт логотипа — Dangrek** (Google Fonts, лицензия SIL Open Font License — коммерческое использование и перевод в кривые разрешены). Опознан 28.08.2026 наложением: контуры совпадают, пропорции отличаются на 9%, что объясняется кеглем.

Начертание в файле переведено в кривые — это осознанно. Живой текст в логотипе зависел бы от загрузки шрифта и прыгал при первой отрисовке.

**Один файл на обе темы** — `src/assets/logo.svg`, слово «Tsugi». Цвет не зашит: в контурах стоит `fill="currentColor"`, а сам цвет приходит из CSS через `color: var(--accent)`. Поэтому логотип автоматически следует за акцентом, включая осветлённый фиолетовый тёмной темы.

**Вставка — компонентом, а не `<img>`.** Через `<img>` картинка грузится как отдельный документ и о цвете страницы ничего не знает: `currentColor` там резолвится в чёрный. Используется `vite-svg-loader`, импорт даёт готовый компонент.

**Имя для скринридера задаётся в месте использования** — `role="img"` и `aria-label` на компоненте, а не элементом `<title>` внутри файла. Причина техническая: `vite-svg-loader` по умолчанию прогоняет SVG через SVGO, а в его наборе `preset-default` есть плагин `removeTitle`, который выбрасывает заголовки без предупреждения. Побочная выгода — имя можно перевести через `t()`, чего статический `<title>` не позволяет. Иероглиф 次 рядом с логотипом скрыт через `aria-hidden`, иначе название читалось бы дважды: словом и знаком.

**Иероглиф 次 — второй знак айдентики**, условный логотип: он же служит фавиконкой. Набран шрифтом Zen Maru Gothic (Google Fonts, SIL Open Font License) и переведён в кривые, файл `logoHieroglyph.svg`.

Устроен так же, как логотип: `currentColor` внутри, вставка компонентом, цвет из CSS. Скрыт от скринридера через `aria-hidden`, потому что имя уже озвучено логотипом.

**Фавиконка — тот же иероглиф**, `public/favicon.svg`. Отличие от логотипа одно, но важное: цвет в ней задан числом (`#7453c1`), а не `currentColor`. Фавиконка рисуется вне страницы, наследовать цвет ей не от чего, и `currentColor` дал бы чёрный. Жирное начертание здесь не украшение, а необходимость: на 16 пикселях тонкие штрихи сливаются.

**Осталось:** добавить `apple-touch-icon.png` 180×180 — iOS не берёт SVG для значка на домашнем экране. Формат `.ico` не нужен: браузеры, которым он требовался, из поддержки давно вышли.


### Принципы

**Поток данных в одну сторону: `api → stores → views/components`.** Компонент не обращается к `api` напрямую, только через стор. Причина практическая: загрузка, ошибка и кеш живут в одном месте. Иначе два компонента, которым нужны одни данные, запросят их дважды и каждый будет крутить свой скелетон.

**Зависимости направлены внутрь.** `api/` не знает о компонентах. `utils/` не знает ни о чём — функции там принимают минимальные структурные типы, а не сгенерированные, и поэтому не ломаются при перегенерации схемы и тестируются без окружения.

**Файл на предмет, а не свалка.** Никакого `utils/index.ts`, куда складывается всё. Имя файла отвечает на вопрос «про что», а не «какого технического рода». Когда в одном файле набирается больше пяти функций про разные вещи — делить по предметам.

**Запросы живут в `api/gql/`, не рядом с компонентами.** Кроме порядка, есть техническая причина: `documents` в `codegen.ts` указывает только на эту папку, поэтому синтаксическая ошибка в компоненте не ломает генерацию типов.

**`api/generated/` не редактируется руками** — при следующем запуске `npm run codegen` правки исчезнут. Файл при этом **коммитится**: иначе сборка на чистой машине и деплой начинают зависеть от доступности AniList. Риск расхождения закрывается проверкой в CI (11.2): перегенерировать и упасть, если результат отличается от закоммиченного. В `.gitattributes` помечен как `linguist-generated`, чтобы не засорять диффы.

**`views/` против `components/`.** В `views/` попадает только то, что подключено в роутере, один файл на роут. Остальное — в `components/`, даже если компонент используется одной страницей. Группировка по папкам внутри `components/` появится, когда их станет больше десятка, не раньше.

**Стили подключаются глобально.** `reset`, `variables` и `mixins` инжектятся в каждый SCSS-блок через `additionalData` в `vite.config.ts`. Поэтому в компонентах можно писать `$base-padding` без импорта — это не магия Vue, а настройка сборки, и о ней надо знать, чтобы не искать несуществующий импорт.

**Заранее ничего не создаём.** `composables/` для переиспользуемой реактивной логики (`useXxx`) появится, когда возникнет второй компонент с одинаковым поведением, а не в ожидании этого.

## 5. Экраны

Для каждого экрана обязательны четыре состояния: **loading**, **error + повтор**, **empty**, **success**. Отсутствие empty- и error-состояний — самая частая претензия на ревью.

### 5.1 Главная `/`

**Зачем этот экран (решено 11.09.2026).** Главная — про **тебя**, расписание — про всех.

Путь к этому ответу стоит записать, чтобы не пройти его второй раз. Сначала главная задумывалась как «что выходит сейчас и что дальше», и пять раскладок подряд получались **уменьшенной копией `/schedule`**: времена, вышло/не вышло, отметка «сейчас». Чем лучше выходила раскладка, тем острее был вопрос, зачем два экрана на один вопрос. Это признак того, что экрану не выдали собственную работу. Работа нашлась в §1: «расписание **с привязкой к личному списку**».

Попутно всплыло то, что надо помнить при любой правке экрана: `airingAt` — это **японский эфир**. Отсчёт до минуты обещает не «через три часа посмотришь», а «через три часа вышло в Японии». Повод не делать из отсчёта главный объект страницы.

#### Одна страница, а не две

Личный блок — **надстройка сверху**; всё ниже одинаково с подключённым списком и без. Двух раскладок не заводим.

Делить на «авторизован / нет» неверно: авторизации в MVP нет (§5.5, §11.3). Деление — «список подключён / не подключён», где список это ник AniList на чтение плюс локальные пометки.

#### Состав сверху вниз

| Блок                          | Когда виден         | Содержимое                                                                                         |
| ----------------------------- | ------------------- | -------------------------------------------------------------------------------------------------- |
| Приглашение подключить список | список не подключён | плашка с кнопкой «Указать ник» и крестиком                                                         |
| «Твои релизы»                 | список подключён    | ближайшая серия из списка крупно с отсчётом; счётчики «выходит сегодня» и «выходит на этой неделе» |
| «Сегодня»                     | всегда              | прокручиваемая полоса обложек по времени                                                           |
| «Всё расписание →»            | всегда              | ссылка на `/schedule?day=` показанного дня                                                         |
| «Популярное сейчас»           | всегда              | баннер с названием на плашке поверх, ниже адаптивная сетка обложек, ссылка на `/search`            |

**Приглашение закрывается навсегда** — булев флаг в `localStorage`. Возвращать его не нужно: канонический вход в список это пункт меню «Мой список» (§5.5). Отключение списка флаг не сбрасывает — это осознанное действие пользователя.

**Ссылка популярного ведёт на `/search`.** Роута `/catalog` нет и в MVP не планируется. Проверять при вёрстке: предыдущая реализация вела на `to="/#"`.

#### Полоса «Сегодня»

Данные из `useScheduleStore` — он уже грузит неделю с кешем и TTL, отдельный запрос не нужен, кеш общий с расписанием.

- **полоса всегда сегодняшняя** (решено 11.09.2026): «Сегодня» значит сегодня. Ни на какой другой день она не переключается, а если сегодня релизов нет — она пустая. Ранее было записано обратное (переключение на ближайший день с релизами) — отменено: подмена дня под неизменным заголовком врёт, а разные дни под одним блоком ломают смысл экрана;
- **прокручивается к границе прошлого и будущего**: к первой непрошедшей карточке, а если сегодня всё вышло — к последней. Одна формулировка вместо веток, и она же верна рано утром, когда граница в начале. Вечером это ещё и по смыслу: последняя вышедшая — самое свежее, что можно пойти смотреть;
- вышедшее держим целиком, приглушённым: оно уезжает влево и остаётся доступным;
- совпадение времени — обычный случай, а не исключение: несколько карточек подряд с одним временем;
- отсчёт только на ближайшей карточке, у остальных время;
- свои тайтлы помечаются как в §5.2: акцентная рамка и бейдж, тот же компонент.

**Наведение на карточку — идея, не реализовано (записано 21.09.2026).** Убрать рамку и подсветку, вместо них — небольшое увеличение обложки. Картинка лежит в обёртке с `overflow: hidden`, поэтому `transform: scale` зумит её внутри рамки кадра: соседи не сдвигаются, потому что трансформация не участвует в раскладке. Переход отключать при `prefers-reduced-motion`.

**Следствие, которое нельзя упустить:** сейчас рамка — это и есть отметка ближайшей карточки. Если убрать её совсем, ближайшую будут выделять только акцентные плашки времени и номера эпизода. Возможно, достаточно; но решение принимать сознательно, а не обнаруживать потом.

**Ближайший релиз ищется по всей неделе, а не внутри дня.** День от этого не меняется — нужно знать, что следующее, даже когда оно уже не сегодня. Три исхода:

| Ближайший      | Что на экране                                                                                               |
| -------------- | ----------------------------------------------------------------------------------------------------------- |
| сегодняшний    | его карточка в полосе получает акцент и отсчёт, к ней же прокрутка                                          |
| не сегодняшний | акцентировать в полосе нечего; рядом с заголовком строка «Следующий выход — завтра в 10:00»                 |
| не найден      | ни акцента, ни строки. Так будет воскресным вечером: ближайший лежит в следующей неделе, которой в кеше нет |

Последний исход — единственное место, где потом пригодится подгрузка соседней недели (`loadWeek` для этого экспортирован). До неё это просто тусклый экран пару часов в сутки, а не поломка.

**Строка про следующий выход — три формы, а не одна** (уточнено 21.09.2026). «Завтра» в примере выше — частный случай: ближайший ищется по всей неделе, поэтому разрыв бывает до шести дней, и в межсезонье пустые дни обычны.

| Разрыв     | Формулировка                                       |
| ---------- | -------------------------------------------------- |
| сегодня    | строки нет, ближайший подсвечен карточкой в полосе |
| +1 день    | «Следующий выход — завтра в 10:00»                 |
| +2…+6 дней | «Следующий выход — в среду в 10:00»                |

Внутри одной недели название дня однозначно, год и число не нужны.

Разрыв считается **в календарных днях**: обе даты через `startOf('day')`, затем `diff`. По часам нельзя — релиз сегодня в 23:00 и завтра в 01:00 разойдутся на два часа и попадут в один день.

**Ловушка локализации:** `dddd` в dayjs отдаёт именительный падеж («среда»), а в строке нужен винительный («в среду»). Либо свои ключи на семь дней в локалях, либо плагин `calendar`, где русские формы уже правильные. В английском проблемы нет.

**Пустое состояние:** «Сегодня релизов нет». Строка про следующий выход при этом остаётся — иначе пустой день превращается в тупик.

**Это не карусель, а прокрутка с маской** (решено 11.09.2026). `n-carousel`, swiper, embla управляют слайдами как страницами и перехватывают touch-события — половину их работы пришлось бы отключать. Нужна обычная прокрутка: инерция на телефоне и стрелки с клавиатуры достаются от браузера бесплатно. Состав — `overflow-x: auto`, спрятанная полоса, затухание по краям через `mask-image`; JS только ради стрелок на ховере и автопрокрутки.

Два требования, которые из этого следуют и легко теряются:

- **затухание обязательно** — пряча полосу прокрутки, мы убираем единственный признак того, что блок листается. При этом затухать край должен только там, где действительно есть продолжение: иначе первая карточка растворяется без причины и выглядит поломкой;
- **тихое обновление по TTL не должно возвращать отмотанную полосу к началу.** Автопрокрутка привязана к смене ближайшей серии, а не к приходу данных.

**Отдельный таймер не нужен.** Граница двигается сама: ближайшая серия вычисляется от `useNow`, он тикает раз в 30 секунд, модуль общий со счётчиком подписчиков. Отсюда же берётся переезд полосы в момент выхода серии — сменился идентификатор ближайшей, сработал `watch`, полоса поехала. Задержка до 30 секунд невидима: отсчёт в минутах.

**Прокрутка к границе сейчас мгновенная всегда** (`behavior: 'instant'`). Для первого позиционирования это верно: плавная на загрузке читается как самопроизвольное движение страницы — человек ещё не понял, что видит, а оно уже едет.

**Открытый вопрос:** тем же `instant` отрабатывает и переезд в момент выхода серии, когда граница сдвигается сама. Там плавность была бы к месту — движение объясняет, что произошло. Чтобы различать, нужен признак «первый вызов или последующий». Не сделано, потому что случай редкий и виден только у того, кто держит страницу открытой.

Перетаскивание мышью на десктопе не делаем: конфликтует с кликом по карточке ради жеста, которого там не ждут. На телефоне достаточно штатной прокрутки.

#### Личный блок «Твои релизы»

Состояний три, третье легко забыть:

| Состояние                             | Что показываем                                                   |
| ------------------------------------- | ---------------------------------------------------------------- |
| список не подключён                   | блока нет, вместо него приглашение                               |
| список есть, релизы есть              | ближайшая серия из списка крупно, отсчёт, два счётчика           |
| список есть, на неделе из него ничего | блок остаётся с текстом «на этой неделе из твоего списка ничего» |

Третье не схлопываем: если блок исчезнет, страница прыгнет и человек решит, что сломалось.

**Крупный блок здесь оправдан, а на общем расписании — нет.** «Следующее вообще» — произвольный тайтл; «следующее у тебя» — твоя подписка, и размер честный.

**Совпадение времени внутри своих** — первая серия в крупном блоке, под отсчётом строка «и ещё одна твоя в 21:00». Второй крупный блок не заводим.

**Счётчики — только два: «Выходит сегодня» и «Выходит на этой неделе».** Оба считаются по уже закешированной неделе, без прогресса: это пересечение списка с расписанием.

**Считаем все серии окна, включая уже вышедшие** (решено 11.09.2026). Следствие, о котором надо помнить: **цифра статична** — за день она не меняется, к вечеру не падает до нуля. Это намеренно, счётчик отвечает «сколько твоего сегодня вообще», а не «сколько ещё ждать».

Отсюда требование к подписи: она обязана читаться как итог, а не как остаток. Отвергнутые формулировки и почему — чтобы не вернулись: «Сегодня из твоего» читается как «сколько осталось»; «Всего сегодня» по-русски переворачивает смысл («всего три» = «целых-то три»). Принадлежность в подписи вообще не нужна — её один раз сказал заголовок блока.

Пара обязана быть параллельной: «Выходит сегодня» и «На этой неделе» устроены по-разному и рядом это видно. Отсюда «Выходит на этой неделе», которое к тому же ровно ложится на английское `Airing today` / `Airing this week`.

**Форма плитки: число плюс строка состава** (решено 11.09.2026) — «3 серии», ниже «2 уже вышли». Так неподвижность числа объясняется на месте, и подпись может быть любой короткой. Два уточнения: строку прятать при нуле, иначе утром она только шумит; когда вышли все — писать «все вышли», а не «3 уже вышли». В недельной плитке строка полезнее, чем в дневной: за неделю доля прошедшего меняется сильнее.

Вариант «двухцветная полоска вместо строки» отвергнут: цвет сам по себе не объясняет, что зелёное значит «вышло», а смысл, переданный только цветом, требует текстовой альтернативы для озвучки — то есть возвращает ту же строку, но уже с украшением сверху.

**Почему не «вышло, не отмечено».** Эта цифра измеряет не реальность, а аккуратность ведения записей, и в MVP она либо чужая, либо выдуманная: запись в AniList требует OAuth, которого нет (§11.3). При чтении по нику прогресс человек ведёт в AniList — мы показываем счётчик долга без кнопки «погасить», да ещё отстающий на TTL. При одних локальных пометках прогресс ведём мы, но вручную отмечать каждую серию никто не станет, и число вырастет в шум.

Идея на потом: **«с прошлого захода вышло N»** — метка времени в `localStorage`, не зависит ни от AniList, ни от дисциплины пользователя. Край: зашёл дважды за час — увидишь ноль.

#### Какой размер обложки брать (замер 22.09.2026)

AniList отдаёт три варианта, размеры измерены:

| Вариант      | Пиксели |
| ------------ | ------- |
| `medium`     | 100×138 |
| `large`      | 230×318 |
| `extraLarge` | 460×636 |

**На телефоне `large` мылит.** Ячейка сетки популярного около 164 логических пикселей, но экраны телефонов двух- и трёхкратные, то есть нужно 328–492 настоящих пикселя. 230 растягиваются, и пиксели видно глазом.

Правило простое: **всё, что крупнее миниатюры, берёт `extraLarge`.** `medium` годится только для строки быстрого поиска, где обложка 40 пикселей шириной. Сейчас `extraLarge` стоит в карточке расписания, а в сетке популярного и в карточке полосы «Сегодня» — `large`, это надо поправить.

#### Что отвергнуто и почему

- **Карусель сегодняшних релизов** — автопрокрутка несовместима с отсчётом: цифра уезжает раньше, чем её успеваешь прочитать. Без автопрокрутки карусель из одного видимого слайда это и есть герой, только с лишними стрелками.
- **Крупный блок «ближайший релиз»** — случайный тайтл получает незаслуженный размер: критерий отбора «первое по часам», а обещание размера — «это важно». И он не один: тайтлы выходят пачками в одно время.
- **Лента-барабан из трёх слотов** с переездом вверх при выходе — то же возражение, плюс упор в край кеша с обеих сторон, плюс анимация, срабатывающая в секунду выхода серии и потому почти никем не виденная.
- **Вертикальная повестка дня** с линией «сейчас» — размазано: всё одного размера, глазу не на чем остановиться. Ушли от неправильного акцента к отсутствию акцента.
- **Крупный отсчёт как якорь страницы** — уцелел только внутри личного блока: без списка он превращал главную в сетку эфира.
- **Баннер для расписания** — в `ScheduleMedia` его нет, а есть он далеко не у всех. Карточка в полосе — просто обложка; `coverImage.color` остаётся подложкой на время её загрузки. Баннер остаётся только у популярного, где он есть в `AnimeCardMedia` и где размер заслужен.
- **Карусель в блоке популярного** — горизонтальное движение на странице должно быть одно, и оно у полосы «Сегодня», где порядок означает время. Сетка из шести: конечное число, `grid-template-columns` вместо состояния, стрелок и `aria`.
- **Корень ведёт прямо на расписание** — рассматривалось дважды, отвергнуто после того, как у главной появилась своя работа. До этого возражение было слабым.

#### Состояния загрузки

Скелетоны на каждый блок независимо; ошибка одного блока не роняет остальные. **Сейчас не выполняется:** блоки смотрят в один `loading` от одного запроса, а ошибка не показывается нигде (§9). Полоса дня и личный блок питаются от одного запроса к `useScheduleStore`, поэтому общий `loading` для них честен; популярное — отдельный запрос, его состояние обязано быть независимым.

#### Порядок работ

Сейчас собираем главную **без личного блока**: приглашение, полоса дня, ссылка на расписание, популярное. Личный блок ждёт `/my-list` и добавляется сверху, ничего не переписывая.

**Что из описанного выше сознательно отложено (на 21.09.2026):**

| Отложено                                    | До чего                                                   |
| ------------------------------------------- | --------------------------------------------------------- |
| Маска и стрелки-затухание по краям полосы   | украшение; полоса листается стрелками и жестом уже сейчас |
| Ссылка «Весь каталог» в блоке популярного   | до экрана `/search`, иначе третий мёртвый переход         |

Остальное из раздела на главной реализовано.

### 5.2 Расписание `/schedule` — ключевой экран

**Режим просмотра нужно отвязать от ширины окна — не сделано (отзыв тестировщика, 22.09.2026).**

Сейчас режим жёстко следует за шириной: шире 1240 — неделя, уже — день. Пользователь не выбирает, за него решает размер окна. На живом сайте это дало сразу четыре претензии, и все они — одна причина с разных сторон:

- не очевидно, что показана именно неделя, — человек её не просил;
- на широком экране нельзя посмотреть один день, такого режима просто нет;
- при изменении ширины экран меняется на другой, и это выглядит как «сайт показывает разное непонятно почему»;
- непонятно, зачем выбирать день в недельной сетке: все семь дней уже видны, а клик только подсвечивает.

**Направление:** явный переключатель «Неделя / День», а ширина задаёт лишь значение по умолчанию. Тогда клик по дню в недельной сетке получает смысл — он переключает в режим этого дня. Состояние остаётся в адресе: к `?day=` добавляется `?view=`.

Пока делается минимальная версия, разворот отложен.

**Широкая раскладка (≥1240px):** сетка из 7 колонок, понедельник — воскресенье. Каждая колонка: заголовок (день недели, число), под ним карточки эпизодов, отсортированные по времени эфира.

**Узкая раскладка (<1240px):** горизонтальная полоса дней недели как навигация (день, число, счётчик релизов), под ней — эпизоды выбранного дня **строчными** карточками: маленькая обложка слева, справа название, номер, состояние и время эфира.

**Почему строчная карточка, а не вертикальная.** Обложка задана пропорцией 2:3, поэтому вертикальная карточка тем выше, чем шире. Замерено 28.08.2026 на экране 375×812: при двух колонках вертикальная карточка выходит 143×277, и на экран помещается **4** штуки; строчная тогда занимала 103px в высоту и помещалась **6**.

**Обложка увеличена с 85 до 120px (30.08.2026), и выигрыш по плотности исчез.** На маленькой обложке тайтл не узнавался, а обложки на этом экране и есть главное содержимое. После увеличения строчная карточка стала 138px, и на 375×812 её помещается **4** штуки — ровно столько же, сколько вертикальных. Замерено на дне с 26 релизами: карточка 359×138, обложка 80×120, то есть 22% ширины карточки; все 26 карточек одной высоты.

Строчную оставляем, но основание теперь другое: **высота строчной карточки не зависит от её ширины**, а у вертикальной растёт вместе с ней. На 375px это паритет, дальше — расхождение. При ширине сетки 654px и двух колонках карточка выходит 323px шириной: строчная остаётся 138px, а вертикальная при пропорции 2:3 вытянулась бы примерно до 560px (расчёт, не замер). Вдобавок название получает всю ширину за вычетом 88px под обложку и почти не ломается на строки.

Карточка одна и та же, переключается пропом `direction` со значениями `column` и `row`: содержимое и логика совпадают, различается только расположение и размер обложки. Отдельный компонент означал бы дублирование `isAired`, `isCurrentDay` и отсчёта.

**Граница взята по замеру, а не по круглому числу.** При семи колонках ширина колонки равна примерно `(ширина экрана − отступы − 6 × 8) / 7`. Замерено 27.08.2026 на неделе со 120 карточками:

| Ширина экрана | Колонка | Подпись «вышло / время»           | Макс. строк в названии |
| ------------- | ------- | --------------------------------- | ---------------------- |
| 1920          | 256px   | в одну строку                     | —                      |
| 1600          | 210px   | в одну строку                     | —                      |
| 1440          | 187px   | в одну строку                     | —                      |
| 1225          | 157px   | в одну строку, 0 из 120 переносов | 5                      |
| 1009          | 126px   | 1 из 120 переносов                | 7                      |
| 768           | 91px    | переносится                       | —                      |

Деградирует не подпись, а **название**: строка «вышло / время» держится до ~126px и ломается только около 91px, а вот заголовок с сужением колонки превращается в лестницу — пять строк на 157px и семь на 126px. Порог выбран по тому, сколько строк названия терпимо.

Граница предварительная — уточняется по ходу вёрстки.

**Список дня — сетка `n-grid` со ступенями `cols="1 650:2"`.** Одна колонка на телефоне, две ближе к порогу раскладки. Третья ступень не нужна: узкая раскладка живёт только до 1240, а на 1240 включается недельная сетка.

**Число 650 — это ширина сетки, а не окна.** У `n-grid` проп `responsive` по умолчанию `self`, то есть ступени сравниваются с шириной самого элемента. Окно шире сетки примерно на 31px — отступы страницы плюс полоса прокрутки, — поэтому вторая колонка появляется около 681px окна. Так надёжнее, чем считать от окна: полоса прокрутки занимает разное число пикселей в разных системах, а отступы страницы меняются между раскладками, и при отсчёте от окна подобранное число тихо перестало бы соответствовать замыслу.

Режим `screen` для числовых ступеней не работает вовсе: в нём Naive передаёт разбору не число, а массив имён своих брейкпоинтов (`s`, `m`, `l`…), числовые ключи не совпадают ни с чем, и сетка молча откатывается к одной колонке. Числа и имена — два разных языка одного пропа.

**Ступень выбиралась по высоте карточек в ряду, но после увеличения обложки это ограничение снялось.** В одной колонке разная высота незаметна, а в двух соседние карточки стоят рядом, и лишняя строка названия ломала ряд. Замерено 28.08.2026 при обложке в 85px, на реальных данных двух дней (14 и 26 релизов):

| Ширина сетки | Ширина карточки | Результат                       |
| ------------ | --------------- | ------------------------------- |
| 809          | 401px           | все карточки 103px, ряды ровные |
| 744          | 368px           | высоты 103 и 118 вперемешку     |

Высоту карточки задавала обложка, пока текст короче неё: отсюда ровные 103px. Третья строка названия выводила текст за её пределы, и карточка сразу вырастала до 118.

Обложка в 120px этот запас закрывает. Замерено 30.08.2026 при ширине сетки 654px: карточки 323×138, самое длинное название занимает три строки — и высота всё равно 138. Текст перестал диктовать высоту, ряды ровные при любой ступени, поэтому ступень опущена с 800 до **650**: теперь она выбирается по плотности, а не по переносам.

Выровнять высоты можно было бы и обрезкой названия через `-webkit-line-clamp` — тогда ступень выбиралась бы только по плотности, а не по переносам. Отвергнуто: в конце названий стоит номер сезона («Season 2»), и обрезка убрала бы именно ту часть, по которой различают тайтлы. По той же причине обрезка не годится и как способ опустить границу раскладки ниже 1240.

Без сетки список выглядит разреженным: на экране 1100px строчная карточка растягивалась на 1065px, а обложка занимала в ней 5% ширины (при обложке в 120px — около 7,5%, то есть проблема осталась той же).

**Перенос дней в несколько рядов отвергнут.** Колонки имеют разную и большую высоту, поэтому второй ряд дней оказался бы не под первым, а ниже всех карточек первого ряда: до пятницы пришлось бы прокручивать весь экран. Это две полунедели друг над другом, а не сетка, и свойство «вся неделя перед глазами» теряется полностью.

**Заголовки дней прилипают в обеих раскладках,** и карточки уезжают под них — при длинном списке видно, к какому дню относится то, что сейчас на экране, а в узкой раскладке день ещё и можно переключить, не возвращаясь наверх.

Липким делается **весь ряд заголовков целиком**, а не каждая колонка по отдельности: заголовки лежат в собственной сетке, отдельной от сетки карточек. Поэтому состояние «прилипло» одно на всю неделю, и класс на него нужен один.

Условия, при которых это работает (проверено на текущей разметке):

- `top` равен высоте шапки приложения, а не нулю: шапка сама `position: sticky`, и при `top: 0` заголовки заедут под неё. Высоту держать в общей CSS-переменной (`--header-height`), иначе она окажется записана в двух местах и разъедется;
- `z-index` строго меньше, чем у шапки (у неё 10) — заголовки должны проезжать под шапкой, а не поверх;
- фон кнопки дня непрозрачный (`var(--surface)`), иначе карточки просвечивают сквозь заголовок;
- ни у одного предка нет `overflow`, отличного от `visible`. Это главная причина, по которой `sticky` молча не работает: элемент прилипает к ближайшему прокручиваемому предку, и `overflow: hidden` выше по дереву запирает липкость внутри него. Сейчас вся цепочка до `html` чистая, прокручивается страница.

**Зазор между шапкой и заголовками закрыт градиентом.** Между ними оставлен отступ, и содержимое, проезжающее в этой полосе, гасится липким градиентом от `var(--bg)` сверху к прозрачности снизу. Слой у него между карточками и заголовками (`z-index` 8 при 9 у заголовков), поэтому даты остаются поверх. Высота больше самого зазора: градиент гасит содержимое ещё и в вертикальных каналах между колонками, где промежуток сетки оставляет карточки видимыми.

Три альтернативы отвергнуты по виду:

- **прозрачный зазор** — в полосе проезжают обрезки названий и подписей, читается как случайная щель;
- **сплошная заливка зазора** — карточки обрываются ровной линией, которой на экране ничто не объясняет, и это выглядит как ошибка отрисовки;
- **прилипание вплотную к шапке** — тесно, и скругление заголовков упирается в её кромку.

Дополнительно у прямоугольной заслонки есть неустранимый конфликт со скруглением: она либо не достаёт до вырезанных углов заголовка, и там видно карточки, либо заезжает на них и закрашивает дугу вместе с рамкой. Градиент от этого свободен, потому что гасит постепенно и не имеет собственной кромки.

Два технических условия для градиента:

- `pointer-events: none` обязателен: полоска лежит поверх карточек, а карточки — ссылки, и без этого свойства клики в её зоне не доходят до цели;
- высоту у потока надо забирать отрицательным `margin-bottom`, а не выводить элемент из потока через `absolute` или `fixed`. `position` одно на элемент, поэтому `absolute` заменит `sticky` и убьёт липкость; `fixed` работает, но не знает границ контейнера и ломается внутри предка с `transform` или `filter`.

**Заголовок дня — кнопка в обеих раскладках.** Клик выбирает день и пишет его в адрес; в узкой раскладке он же переключает список. На широком экране видимого эффекта почти нет, и это осознанная цена: выбор переживает изменение размера окна — выбрал среду на ноутбуке, сузил окно, открылась среда, а не сегодня. Обратный вариант, при котором заголовок на широком экране нарисован как карточка с рамкой и фоном, но не нажимается, даёт ложное обещание: тот же элемент в узкой раскладке внезапно становится рабочей кнопкой.

**Две подсветки, как в датапикере:** сегодняшний день — акцентный цвет текста; выбранный день — рамка и фон. Роли разные, поэтому и приёмы разные: первое сообщает факт о расписании, второе показывает состояние экрана.

**Кнопки шапки растягиваются только тогда, когда переносятся на свою строку.** Заголовок и блок кнопок лежат в одном флекс-контейнере с переносом; обоим задан `flex-grow`, но в соотношении 15 к 1. На общей строке заголовок забирает почти весь свободный остаток, кнопкам достаётся считаное число пикселей — на 1400px блок вырос на 49px, и весь прирост ушёл в «Сегодня», стрелки остались по 51px. Когда кнопки переносятся, они оказываются на строке одни, делить не с кем, и весь остаток достаётся им. Медиазапрос при этом не нужен: правило выражено приоритетами роста.

Блоку кнопок задан `flex-shrink: 0` — иначе при нехватке места он сожмётся вместо переноса, и стрелки станут уже задуманного.

Размер кнопок — `large`, то есть 40px по штатной шкале Naive (`small` 28, `medium` 34). До рекомендованных для сенсорного нажатия 44px не дотягивает, но это штатный размер без ручной подгонки паддингов.

**Заголовок остаётся недельным в обеих раскладках.** Вариант с названием выбранного дня («четверг, 3 сентября») рассматривался и отвергнут: полоса дней и так показывает, какой день выбран, а строка «Расписание + диапазон» помещается в одну строку даже на 345px — замерено 29.08.2026, 278px из 359 доступных. По той же причине слово «Расписание» на узких экранах не скрывается.

**Сокрытие шапки приложения при прокрутке отложено.** Залипшая часть занимает 186px из 812 на телефоне, то есть 23% экрана, и соблазн вернуть их есть. Но приём требует отслеживания направления прокрутки с гашением дребезга, а выигрыш — 60px из 812. Делать имеет смысл в рамках отдельной мобильной итерации, вместе с общей перерисовкой, а не точечно.

**Контракт `?day=`.** В адресе живёт **один** параметр — выбранный день, строго `YYYY-MM-DD`, разбор с флагом строгости (`dayjs(raw, 'YYYY-MM-DD', true)`). Неделя из него вычисляется, а не хранится рядом.

Почему один параметр, а не `week` + `day`: два параметра порождают вопросы без хороших ответов — какой день выбран, если открыта не текущая неделя; что главнее при `?week=2026-08-24&day=2026-09-15`. С одним параметром эти состояния невозможны по построению. Второе следствие важнее: смена раскладки перестаёт быть переносом состояния между режимами — данные и выбранный день те же, меняется только способ показа.

Любое другое значение — мусор, несуществующая дата, чужой формат, повтор параметра, пустое значение, отсутствие параметра — трактуется как сегодня, молча, без сообщения пользователю. Обоснование: адрес формирует само приложение через `toDateKey`, руками его никто не вводит, поэтому нарушение контракта означает битую ссылку, а не ошибку пользователя, и объяснять её некому.

Строгость обязательна: без флага dayjs разбирает мягко и «перекатывает» несуществующие даты через границу месяца — `2026-13-01` превращается в 1 января 2027, а голое число `1755550000` в 1759 год. Экран при этом выглядит рабочим, потому что год в интерфейсе не выводится.

Ключ кеша остаётся недельным и каноническим — понедельник по `isoWeek`, `getStartOfWeekDate` в `utils/dates.ts`. Семь разных значений `day` внутри одной недели дают один ключ и один запрос к API.

**Диапазон просмотра ограничен только вперёд — на полгода от сегодняшнего дня.** Назад ограничения нет.

Граница вперёд защищает не от плохих данных, а от бесконечности: листать можно сколько угодно, и каждая неделя — отдельный запрос к API с минутным лимитом. Назад ограничения нет, потому что прошлое не протухает: данные там реальные и уже не изменятся, а сохранённая полгода назад ссылка на прошлую неделю обязана открыться.

**Как на самом деле убывают данные вперёд.** Замерено 28.08.2026, эпизодов в неделе:

| Недель вперёд | Дата   | Эпизодов |
| ------------- | ------ | -------- |
| 0             | 28 авг | 100+     |
| 4             | 25 сен | 100+     |
| 8             | 23 окт | 100+     |
| 12            | 20 ноя | 48       |
| 16            | 18 дек | 37       |
| 20            | 15 янв | 14       |
| 26            | 26 фев | 12       |
| 39            | 28 мая | 7        |
| 52            | 27 авг | 5        |

Полная сетка держится около двух месяцев, к трём ужимается вдвое, обвал приходится на четвёртый-пятый месяц. Но до нуля не доходит **никогда**: даже через год в неделе остаётся пять-семь эпизодов — долгоиграющие сериалы, расписанные далеко вперёд.

Отсюда следствие: **пустые недели в будущем практически не встречаются**. У границы диапазона пользователь увидит не пустой экран, а редкую неделю с несколькими карточками, что понятно само по себе. Поэтому отдельное сообщение «расписание на этот период ещё не опубликовано» не нужно: случай, ради которого оно задумывалось, почти недостижим. Хватает одного варианта — «на этой неделе релизов нет», и он покрывает и межсезонье, и редкую пустую неделю в будущем.

Дата за верхней границей трактуется как сегодня — так же, как мусор. Обоснование строгое: приложение формирует адреса только из стрелок, а стрелки за границу не выходят; со временем будущая дата не отдаляется, а приближается. Значит адрес дальше границы не мог быть выдан приложением ни в какой момент прошлого — он набран руками.

Граница отсчитывается от сегодняшнего дня и вместе с ним двигается. Стрелка «следующая неделя» на границе гасится — так же, как гаснет «Сегодня» на сегодняшнем дне; правило не нужно объяснять словами, оно видно по неактивной кнопке.

**Поведение навигации:**

- стрелки сдвигают на ±7 дней, сохраняя день недели: смотрел пятницу — попадёшь на пятницу. Вариант «понедельник новой недели» отвергнут: любая ссылка с широкого экрана открывалась бы в узкой раскладке понедельником;
- кнопка «Сегодня» пишет сегодняшнюю дату и заблокирована, когда сегодняшний день уже выбран. Подпись одна для обеих раскладок: кнопка пишет именно дату, а не понедельник недели, поэтому «Сегодня» описывает её точно. Блокировка тоже дневная, а не недельная: выбранный день заметно помечен рамкой и фоном, поэтому пользователь видит, совпадает ли он с сегодняшним. При недельном условии возникал рассинхрон — стоя на понедельнике текущей недели, нельзя было вернуться на сегодня, потому что кнопка была погашена;
- переключение дня — `router.replace`, а не `push`: в узкой раскладке это частое действие, и «назад» должно возвращать на предыдущий экран, а не отматывать дни по одному. То же правило, что для фильтров поиска (5.3). Стрелки недель, наоборот, идут через `push`: это осознанный переход на другой отрезок времени, и возврат к предыдущей неделе кнопкой «назад» ожидаем.

**Элементы:**

- **Шапка:** диапазон недели («27 июля — 2 августа»), кнопка-стрелка «<», кнопка «Сегодня», кнопка-стрелка «>». Кнопка заблокирована, когда выбран сегодняшний день, — она же служит индикатором того, где пользователь находится.
- **Фильтр «Только мой список»** — переключатель, состояние в query-параметре. Источник списка — слияние публичного списка AniList по нику и локальных пометок (5.5). Если ни ника, ни локальных пометок нет — подсказка со ссылкой на «Мой список», а не пустая сетка.
- **Сегодняшний день** помечен акцентным цветом текста и полосой в 5px по нижнему краю кнопки, выбранный — рамкой и фоном (см. правило двух подсветок выше). В широкой раскладке пометка «сегодня» относится к колонке, в узкой — к элементу полосы дней. Полоса рисуется тем же приёмом, что и метка «вышло» на карточке, только акцентным цветом: `color-mix(--accent 80%, transparent)`.
- **Карточка эпизода (`EpisodeCard`)**: обложка, название, номер эпизода, время эфира в локальной зоне пользователя. Тайтлы из личного списка помечены акцентной рамкой и бейджем.

**Решение по обложкам: `object-fit: cover` + поле `extraLarge`.** Слот задан через `aspect-ratio: 2 / 3`, поэтому на 1920px карточка получается 236×354.

Замерено 19.08.2026 — во сколько раз исходник масштабируется (↑ растягивание и мыло, ↓ уменьшение и резкость):

| Комбинация               | Вертикальные | Горизонтальные |
| ------------------------ | ------------ | -------------- |
| `cover` + `large`        | ×1.10 ↑      | ×2.72 ↑        |
| `cover` + `extraLarge`   | ×0.55 ↓      | ×1.37 ↑        |
| `contain` + `large`      | ×1.03 ↑      | ×1.03 ↑        |
| `contain` + `extraLarge` | ×0.51 ↓      | ×0.51 ↓        |

Из 127 обложек экрана 124 вертикальные (около 0.71) и 3 горизонтальные (до 1.77). `large` — 230px по ширине, `extraLarge` — 460px, то есть вчетверо больше пикселей.

Почему так: при карточке 236px `large` не хватает даже вертикальным. Горизонтальные при обрезке остаются слегка мягкими при любом разрешении — вписать кадр 1.77 в слот 0.67 требует увеличения, и это свойство обрезки, а не разрешения.

Открытая альтернатива, если понадобится ускорить загрузку: заменить `aspect-ratio` на фиксированную `height` у обёртки. Тогда высота слота перестанет зависеть от ширины колонки, миниатюру можно сделать меньше, и `large` начнёт уменьшаться, а не растягиваться. Сетку менять при этом не нужно.
- **День без релизов** — колонка остаётся на месте с текстом «нет релизов». Дни не выпадают из сетки.

**Состояния эпизода — три правила, у каждого своя область действия:**

| Что                               | Когда показывается                | Зачем                                                             |
| --------------------------------- | --------------------------------- | ----------------------------------------------------------------- |
| Время эфира                       | всегда                            | базовая информация                                                |
| Метка «вышло»                     | эпизод в прошлом, любая неделя    | констатация факта, не требует сравнивать время с текущим в голове |
| Обратный отсчёт «через N ч M мин» | эпизод **сегодня** и ещё не вышел | отвечает на вопрос «что ещё выйдет сегодня»                       |

Логика в одну фразу: **прошлое помечаем, ближайшее будущее считаем, далёкое просто показываем.**

Почему отсчёт ограничен сегодняшним днём, а не всей неделей: «через 84 дня» на карточке из будущей недели бесполезно, а 96 одинаковых подписей на экране — шум. Ограничение сегодняшним днём само себя гасит к ночи, когда всё уже вышло.

**Приглушение вышедших отменено 28.08.2026.** Раньше карточки вышедших эпизодов на текущей неделе получали `opacity: 0.6`. Правило снято по трём причинам.

Контраст. Прозрачность действует на всё содержимое сразу, включая текст, который и так приглушён `depth="3"`, и эффекты складываются. Замер по токенам темы:

| Элемент                | Обычно | При `opacity: 0.6` |
| ---------------------- | ------ | ------------------ |
| Название, светлая тема | 15.51  | 4.17               |
| Подпись, светлая тема  | 5.64   | 2.50               |
| Название, тёмная тема  | 11.38  | 5.04               |
| Подпись, тёмная тема   | 5.21   | 2.78               |

Норма WCAG AA для обычного текста — 4.5. Подписи уходили вдвое ниже нормы, название в светлой теме — тоже под порог.

Охват. Приглушение задумывалось как сигнал, но к середине недели накрывало от трети до половины карточек, а к воскресенью почти все. Признак, относящийся к большинству элементов, не выделяет, а просто делает страницу тусклее. В узкой раскладке, где виден один день, приглушённые карточки идут сплошным блоком сверху — контраста не возникает вовсе.

Избыточность. Метка «вышло» с галочкой сообщает то же самое однозначно и не трогает обложки, которые на этом экране и есть главное содержимое.

Побочно упростилась модель: исчезло правило «приглушение только на текущей неделе», а вместе с ним — проп `isCurrentWeek`, который тащился из вьюхи через сетку в каждую карточку.

**Замена приглушению — цветная полоса по краю карточки.** Подсмотрено 28.08.2026 у yummyani.me: там вышедший эпизод помечен полосой `border` в 5px по правому краю карточки, а не приглушением; фон и прозрачность у вышедших и предстоящих одинаковые. Приём решает ту же задачу, но добавляет метку вместо ослабления всей карточки, поэтому обложка и текст не теряют контраст.

Для нас: полоса **справа** в строчной карточке узкой раскладки и **снизу** в вертикальной карточке сетки — по той стороне, вдоль которой карточки выстроены, чтобы полосы читались как общая шкала. Цвет — `--success`. Полоса стоит на границе карточки, поэтому контраст проверяется к обоим соседям — и к карточке, и к фону страницы. Метка «вышло» текстом остаётся.

Асимметрия намеренная: цветом помечается **прошлое**, будущее не помечается ничем. Помечаем то, что произошло, а не притеняем то, что ещё не наступило.

**Счётчик релизов — бейдж-пилюля** на углу кнопки дня, вместо третьей строки внутри неё. У Naive для этого есть `n-badge`. Плюс: не занимает высоту кнопки и заметнее. Минус, который надо проверить на вёрстке: при двузначных числах пилюля вылезает за габарит кнопки и на узких экранах может задевать соседний день.

**Кандидат на будущее — фильтр «уже вышедшие» с тремя состояниями** (только вышедшие / только предстоящие / все). Идея, не решение; открытые вопросы записаны в «Осталось».

**Формат отсчёта.** До часа — минуты, до суток — часы и минуты, дальше — дни. Сокращения («мин», «ч», «дн») вместо полных слов: они не склоняются, поэтому не требуют настройки множественных форм в `vue-i18n`, и строка короче — меньше переносов в узкой карточке. Минуты округлять вверх, иначе последнюю минуту видно «через 0 мин».

**Группа отсчёта не переносится и не сжимается — уступает время эфира.** Критерий приёмки: подпись вида «через 12 ч 25 мин» всегда стоит одной строкой; если места не хватает, на вторую строку уходит время эфира, и это нормально. Обратное — разрыв внутри самой подписи — считается дефектом.

Специальных правил в CSS для этого нет, потому что сейчас требование выполняется само, за счёт запаса по ширине. Проверено 29.08.2026 на всех карточках с отсчётом и подстановкой худшего текста «через 23 ч 59 мин»: группа стоит одной строкой (17px) вплоть до карточки в 120px, а колонка в широкой раскладке не бывает уже 157px. Запас появился не намеренно — он следствие того, что порог раскладки опустился с 1400 до 1240 и минимальная колонка выросла.

Если порог когда-нибудь опустят ниже, запас исчезнет, и тогда понадобятся `flex-shrink: 0` у группы — чтобы при нехватке места уступало время эфира, а не сжималась подпись, — и `white-space: nowrap` у самих подписей. Одного `:wrap="false"` для этого мало: он запрещает элементам группы разъехаться на несколько флекс-строк, но не мешает сжать саму группу, а сжатая группа ломает текст внутри каждого `n-text` — «25» и «мин» оказываются на разных строках.

Измерять этот дефект надо аккуратно: замер высоты строки показывает его не всегда — вместо переноса флексы могут просто сжать элементы, высота останется односрочной, а текст вылезет за границу. Мерить нужно ширину, требуемую группе, через клон с `width: max-content`, и обязательно на худшем тексте. На среднем случае дефект не воспроизводится.

Замерено 27.08.2026, ширина, нужная группе одной строкой:

| Подпись           | Группа | Карточка | Экран при 7 колонках |
| ----------------- | ------ | -------- | -------------------- |
| через 25 мин      | 105px  | 121px    | ~935                 |
| через 1 ч 5 мин   | 120px  | 136px    | ~1040                |
| через 12 ч 25 мин | 135px  | 151px    | ~1145                |
| через 23 ч 59 мин | 135px  | 151px    | ~1145                |

Физический минимум для широкой раскладки — около 1145px; выбранная граница 1240 даёт карточку ~165px, то есть запас 14px. При этом на 1240 группа плюс время требуют ~177px, поэтому у двухчастных отсчётов время эфира уедет на вторую строку и такие карточки станут на строку выше соседних. Касается только сегодняшних невышедших эпизодов — единиц из сотни.

**Тикер.** Один на приложение — композабл с общим `now` на уровне модуля и счётчиком подписчиков; интервал создаётся первым подписчиком и убивается последним. Частота 30 секунд: секунд в подписи нет, обновлять чаще незачем.

**Навигация:** клик по карточке ведёт на `/anime/:id`.

**Подскролл к ближайшей серии — идея, не реализовано (записано 21.09.2026).** В день бывает под тридцать релизов, и открывая расписание человек попадает в начало списка, то есть на давно вышедшее. Правило формулируется так: **если выбранный день — сегодня, при открытии экран подскролливает к первой непрошедшей серии.** Привязывать это к переходу с главной не стоит — пришлось бы тащить признак через навигацию, а поведение должно быть одинаковым и по ссылке «Всё расписание», и при заходе прямо на `/schedule`.

Смежное: та же граница прошлого и будущего уже используется полосой «Сегодня» на главной (5.1), так что вычисление переиспользуется. Открытый вопрос — как это уживётся с липкими заголовками дней: подскролл должен оставлять карточку под заголовком, а не за ним.

**Состояния:** скелетон-сетка из 7 колонок; ошибка с кнопкой повтора; «на этой неделе релизов нет» (реально бывает в межсезонье).

### 5.3 Поиск

Поиск разделён на два: быстрый в шапке и подробный на отдельной странице.

#### Быстрый поиск в шапке

Только по тексту, без фильтров. Набрал — увидел список тайтлов — выбрал — попал на страницу тайтла.

На подробный поиск ведут два входа: **Enter** с набранным текстом (`/search?q=…`, запрос не теряется) и **кнопка** рядом с полем, работающая в любой момент, в том числе до ввода — тогда открывается пустой каталог по фильтрам.

- **Выбор пункта — это переход, а не подстановка текста.** Строка при этом сохраняется (решено 10.09.2026): шапка живёт над всеми экранами, и запрос в ней остаётся рабочим состоянием — открыл тайтл, вернулся, выбрал соседний, не перенабирая. Ранее планировалось очищать; отменено.
- **Состояние в адрес не пишется** — единственное место, где общее правило (см. ниже) не действует. Строка живёт секунды и умирает с выпадашкой, пересылать её незачем.
- **Ответы обязательно упорядочиваются.** Дебаунс уменьшает число запросов, но не порядок ответов: дописал букву — и ответ на прежнюю строку может прийти позже и перетереть свежий. Нужна отмена предыдущего запроса.
- Минимальная длина строки — два-три символа, иначе одна буква вернёт мусор и сожжёт лимит запросов.
- Запрос маленький: `search` и только то, что рисуется в строке — id, название, год, формат, маленькая обложка.
- Всплывашка при ошибке здесь уместна: действие инициировал пользователь, а места под состояние ошибки в выпадашке нет.
- **У Enter два смысла**, и различает их подсветка в выпадашке: подсвечен пункт — открывается тайтл, не подсвечен — переход на подробный поиск. Выбор по Enter у `n-auto-complete` встроенный, поэтому надо проверить на практике, отдаёт ли он событие только при подсветке.

**Открыто:** очищать ли поле шапки при переходе на подробный поиск. В отличие от выбора тайтла запрос здесь не израсходован, а поехал дальше. Если на `/search` будет своя строка поиска, два одинаковых поля рядом излишни и шапку логично очистить; если своей строки не будет — шапка остаётся единственным местом, где виден запрос. Решается вместе с вёрсткой `/search`.

**Мобильная вёрстка шапки — отдельным заходом** (решено 10.09.2026). Поле не помещается на узком экране (на 375px плейсхолдер обрезан), а рядом должна встать ещё и кнопка подробного поиска; обычное решение — сворачивать поиск в иконку, раскрывающую поле на всю ширину поверх шапки. Сначала делается сам поиск на широком экране, перекройка шапки — потом, чтобы не мешать две разные задачи.

#### Подробный поиск `/search`

**Фильтры:** строка поиска, жанры (мультиселект), год, сезон, формат (TV / Movie / OVA / ONA / Special), статус, сортировка (популярность / рейтинг / дата выхода).

**Требование:** все фильтры отражаются в query-параметрах URL и восстанавливаются из них при загрузке страницы. Ссылку с фильтрами можно скопировать и открыть в другой вкладке — состояние совпадёт. Синхронизация двусторонняя: изменение фильтра → `router.replace` (не `push`, чтобы не засорять историю); переход «назад» → фильтры перечитываются из URL.

**Ввод в строку поиска** — дебаунс 400 мс. Отмена предыдущего запроса при новом вводе (гонки ответов недопустимы: медленный ответ на старый запрос не должен перетирать свежий).

**Пустая строка поиска допустима** (решено 10.09.2026): фильтры работают сами по себе, и экран в этом режиме превращается в каталог. Значит «ничего не введено» — не отдельное состояние, а обычная выдача по текущим фильтрам.

**Выдача:** сетка карточек. Способ дозагрузки не выбран, склоняемся к пагинации.

**Что важно в этом выборе (разбор 10.09.2026, по замерам на чужих сайтах).** Существенно не «пагинация против прокрутки», а **сохраняется ли выдача при возврате с деталей тайтла** — это самое частое действие на экране поиска. Оба подхода встречаются в живых проектах, но бесконечная прокрутка требует отдельной работы, без которой ломается: замеренный пример — сто двадцать загруженных карточек превращаются в сорок, прокрутка сбрасывается в ноль. Реализации, которые это делают правильно, тоже есть, там возврат отдаёт и полную выдачу, и точную позицию.

Отсюда две согласованные пары:

- **пагинация**: номер страницы и есть состояние, он ложится в адрес, возврат работает сам, перезапрос одной страницы дешёвый. Ничего доделывать не надо;
- **прокрутка или «показать ещё» + выдача в сторе**: приятнее в браузении, но нужен `scrollBehavior` роутера с сохранённой позицией, и карточки обязаны отрисоваться из стора **до** восстановления позиции — иначе прокручивать нечего и позиция теряется.

Требование «состояние в адресе» полностью выполнимо только в первом варианте: номер страницы в адрес ложится, «прокручено до 200-й карточки» — нет.

**Состояния:** loading (скелетоны), «ничего не найдено» с подсказкой сбросить фильтры, ошибка.

### 5.4 Детали `/anime/:id`

**Раскладка утверждена 22.09.2026.** Сверху вниз:

1. **Баннер** `bannerImage` во всю ширину. Высоту задавать от ширины окна с ограничителями (форма записи — `clamp(140px, 18vw, 340px)`), а не числом: фиксированный пиксельный размер на широком экране превращается в полоску. На пропорции исходника опираться нельзя — замер шести баннеров 22.09.2026 дал 1900×400 у большинства, но попались 1800×550 и 1721×391. Значит `object-fit: cover` в нашей коробке. Выше 1900px по ширине источник растягивается сверх собственного размера — это либо потолок высоты, либо ограничение ширины контента.
2. **Обложка** `extraLarge` отрицательным отступом наезжает на баннер снизу. Справа от неё — название по локали (`english` или `romaji`), под ним `native`, ниже бейджи: формат и год, статус, `averageScore`.
3. **Полоса ближайшей серии** во всю ширину, акцентная: «Серия 13 выйдет в четверг, 24 сентября, в 18:30», второй строкой — «через 2 дня». Данные берутся из `nextAiringEpisode`, **а не из первой будущей записи расписания**: у длинных сериалов список начинается позапрошлым годом.
4. **Две колонки**: слева факты шириной 210px, справа жанры и описание с сворачиванием.
5. **Блок «Ближайшие выходы»** под разделителем, во всю ширину.

Раскладка без баннера отвергнута: отдельной вёрстки для этого случая не делаем. Но **пустой `bannerImage` — не редкость**, как считалось сначала: он редок только в верхушке каталога.

| Срез популярности | С баннером | С трейлером |
| ----------------- | ---------- | ----------- |
| места 1–25        | 25 / 25    | 24 / 25     |
| места 351–400     | 50 / 50    | 44 / 50     |
| места 1201–1250   | 49 / 50    | 42 / 50     |
| места 2951–3000   | 38 / 50    | —           |

Замер 02.10.2026 на глубине каталога: баннера нет у двенадцати тайтлов из пятидесяти, почти у четверти. Значит запасной вариант — не страховка на всякий случай, а то, что увидит заметная часть посетителей.

Запасной вариант при `bannerImage: null` — плашка цвета `coverImage.color`, без смены раскладки. Проверено на «SHIROBAKO Movie»: выходит ровная цветная полоса, обложка на ней читается.

**Если нет и цвета — красим акцентным.** Решено 05.10.2026. У части тайтлов `coverImage.color` тоже равен `null`: замер по трём срезам каталога нашёл одиннадцать таких, среди них и свежие 2025–2026 годов, то есть дело не в возрасте записи. Тогда баннер заливается `var(--accent)` — получается фиолетовая полоса, которая читается как часть оформления, а не как сбой.

**Ловушка, из-за которой это не работало раньше.** Запасное значение в CSS срабатывает, только когда свойство **не установлено вовсе**. В `bannerStyle` стояло `?? 'transparent'`, то есть `--cover-color` выставлялось всегда, и запись `var(--cover-color, #000)` в градиенте была мёртвой: затемнение считалось от прозрачного, у которого нет ни тона, ни насыщенности, отсюда и серая муть. Теперь там `?? undefined` — Vue такое свойство не выводит, и запасное значение ожило.

**Меняется только фон, не затемнение.** Градиент по смыслу нейтральная вуаль для текста; подкрашивать его цветом обложки — украшение, а не необходимость. Проверено: при акцентном фоне разница между нейтральным и акцентным затемнением на глаз неразличима, потому что светлота там 0.12.

**Факты в левой колонке:** студия (`isMain`), число эпизодов, длительность, сезон, начало показа, первоисточник, «в списках» (`popularity`). Вторую оценку не выводим: `averageScore` уже стоит в бейдже, два процента подряд ни о чём не говорят.

**Действий на странице нет — она читательская.** Слот под будущие кнопки `/my-list` зарезервирован под обложкой, над колонкой фактов: ширина обложки задаёт ширину кнопки даром, а её появление сдвинет вниз только колонку фактов, не трогая шапку с длинным названием. **Заглушку не рисовать** — ни неактивной кнопки, ни надписи «скоро»: пустое место читается как законченная страница, серая кнопка — как брошенная работа.

Внешнюю ссылку на AniList не ставим: отправлять зрителя туда, откуда мы сами протаскиваем данные через прокси (6.2), странно, а указание источника — это строка в подвале, а не кнопка на каждой странице.

#### Блок «Ближайшие выходы»

Форма — список строк «серия N — день недели, дата — время — через сколько». Горизонтальная лента отвергнута: внутри одного тайтла плитки отличаются только датой, и жест прокрутки ради четырёх дат не окупается.

Правила:

- **Рендерится при `nextAiringEpisode !== null`.** Условие на статус хуже: оно выбрасывает анонсированные тайтлы с известной датой премьеры, у которых список тоже осмысленный.
- **Скрывается при одной будущей серии** — она уже написана в полосе выше, блок из одной строки дублирует её.
- **Запрос — `airingSchedule(notYetAired: true)`, ровно одна страница.** Пагинация не нужна: замер по двенадцати самым популярным выходящим дал `hasNextPage: false` у всех, включая One Piece с его двадцатью тремя сериями впереди.
- **Прогресс «вышло N из M»** считается из `nextAiringEpisode.episode - 1`, отдельный запрос не нужен. У длинных сериалов `episodes` бывает `null` — тогда «из M» пропадает.

Полного списка всех серий не делаем. Замеры 22.09.2026 показали, почему:

| Тайтл                     | Статус    | Серий | Записей | Что не так                        |
| ------------------------- | --------- | ----- | ------- | --------------------------------- |
| Dandadan (2024)           | FINISHED  | 12    | 12      | всё ровно                         |
| Sousou no Frieren (2023)  | FINISHED  | 28    | 24      | нумерация начинается с 5          |
| Shingeki no Kyojin (2013) | FINISHED  | 25    | 0       | расписания нет вовсе              |
| DEATH NOTE (2006)         | FINISHED  | 37    | 0       | расписания нет вовсе              |
| ONE PIECE                 | RELEASING | null  | 80      | `pageInfo` врёт, страницами по 25 |

Отсюда три правила, которые действуют, даже если блок когда-нибудь расширят:

- **Нумеровать серии циклом от 1 до `episodes` нельзя.** У Frieren первые четыре серии показали одним блоком, поэтому записи начинаются с пятой. Рисовать только то, что пришло.
- **У тайтлов примерно до 2015 года расписания нет вовсе.** Пустой список — норма, а не ошибка.
- **`pageInfo` вложенного `airingSchedule` недостоверен.** На третьей странице One Piece он отдаёт `total: 500, lastPage: 20, hasNextPage: true`, при этом на четвёртой приходит пять записей, а дальше пусто; `total` между одинаковыми запросами показывал то 450, то 500. Признак конца — пришло меньше 25 записей. Аргумент `perPage` во вложенной связи игнорируется и режется до 25.

#### Трейлер — низкий приоритет

Поле `trailer` заполнено почти всегда: 24 из 25 в топе популярности, все — YouTube, у всех есть `thumbnail`. Место блока — правая колонка, под описанием.

**Делаем последним**, после всего остального на странице. Сначала блок вовсе отвергли, потом решение пересмотрели в тот же день — рассуждение стоит сохранить целиком, потому что оно не про технику.

YouTube из России без VPN замедлен: страница `youtube.com/embed/ID` встраивается без проблем, а сегменты видео идут с `googlevideo.com`, и деградирует именно этот слой. Переписыванием на Vercel (6.2) это не лечится: правило перехватывает адреса нашего домена, а за сегментами браузер зрителя пойдёт напрямую. Насколько плохо — зависит от провайдера и времени суток, у кого-то видео идёт в низком качестве, у кого-то крутится загрузка.

Отказались от блока не поэтому, а решили, что мёртвый блок хуже отсутствующего. Возражение оказалось сильнее: **неиграющий ютубовский плеер зритель относит на счёт YouTube, а не нашего сайта.** Все знают, как он себя ведёт без VPN, и никто не сочтёт это дефектом приложения. Цена ошибки почти нулевая, значит блок имеет смысл.

**Встраиваем по клику, а не при открытии страницы.** Сначала превью с кнопкой воспроизведения, `<iframe>` создаётся только после нажатия. Выигрыш не зависит от блокировок: плеер тянет скрипты и куки третьей стороны, то есть YouTube получал бы данные обо всех, кто просто пролистал страницу и не собирался смотреть. Плюс вес — бандл и так 1.32 МБ (9).

Две засады при реализации:

- **В `trailer.id` приходит мусор, но сам по себе он безвреден.** У «Атаки титанов» он приходит как `"LHtdKWJdif4\t"` — с табуляцией на конце, в экранированной записи она видна, в самой строке нет. Разбор адресов по стандарту WHATWG вырезает табуляции и переводы строк из URL целиком, и браузер применяет это к `src` у `<iframe>` и `<img>` — поэтому склеенный адрес работает и на AniList, и у нас, и готовый `thumbnail` от AniList тоже не битый. Сломать можно ровно одним способом: прогнать идентификатор через `encodeURIComponent` — тогда табуляция станет `%09`, переживёт разбор и даст ссылку на несуществующее видео. Отсюда правило: **идентификатор не кодировать**, а `.trim()` держать как гигиену.
- **`trailer.site` в теории бывает `dailymotion`.** В выборке из 25 таких не было, но поле это допускает — либо отдельная ветка, либо явный пропуск не-YouTube.

Превью пойдёт через собственное правило для `i.ytimg.com` в `vercel.json` (6.2): картинки замедляются так же, как видео, а через машину Vercel проходят.

#### Взрослый контент

В расписании и поиске `isAdult` отсекается раньше (5.2, 5.3), но на детали можно прийти по прямой ссылке мимо всех фильтров. Поэтому запрос берёт `isAdult`, и при `true` баннер и обложка размываются, а поверх каждой ложится кнопка-накладка.

Решено 22.09.2026:

- **Это визуальный барьер, а не проверка возраста.** Настоящей верификации нет, и заявлять её нельзя. Задача — не показать случайно.
- **Клик по любой из двух накладок открывает подтверждение** (`n-popconfirm` рядом с картинкой, не модалка на весь экран). Согласие снимает обе накладки разом — состояние у них общее.
- **Флаг один на всё приложение**, в `localStorage`. Подтвердили — больше не спрашиваем ни на других тайтлах, ни в других вкладках. Сессионное хранилище отвергнуто замером 02.10.2026: оно живёт в пределах одной вкладки, в новой возвращает `null`, а карточки тайтлов открывают в новых вкладках пачками — человек получал бы накладку на каждой. Хранится не признак, а **момент, до которого подтверждение действует** — сутки от нажатия. При чтении значение сравнивается с текущим временем, просроченное считается отсутствующим. Так барьер возвращается сам на общем компьютере, а человеку, читающему каталог за один вечер, переспрашивать не приходится.
- Мусор в хранилище отдельной проверки не требует: `Number()` от чужого значения даёт `NaN`, а сравнение с ним всегда ложно — значение окажется просроченным само собой.
- Обращение к `localStorage` оборачивать в `try`: в приватном окне и при запрете на данные сайта оно бросает исключение. При неудаче считаем, что подтверждения нет.
- **Называть флаг по смыслу** — подтверждение возраста, а не «показать обложку». Если когда-нибудь перестанем фильтровать взрослое в поиске, он переиспользуется там же.
- **Размытие косметическое.** Адрес обложки лежит в DOM, файл скачивается целиком. Если задача сменится на «не отдавать», надо не подставлять `src` до подтверждения — это другой механизм.
- **Накладка — настоящая `button`** с `aria-label`, а не `div` с обработчиком: иначе до неё не добраться с клавиатуры.
- `filter: blur()` подмешивает к краям прозрачность и даёт светлую кайму. Лечится увеличением размытого слоя и `overflow: hidden` на обёртке.
- Тексты — в локали, обе.

Пути назад после подтверждения нет: накладка исчезает вместе с местом под кнопку. Для сессионного согласия это принято сознательно.

#### Состояния

Загрузка — скелетоны. Отдельно нужно **отличать «нет такого тайтла» от обрыва связи**: на списочных экранах разницы нет, здесь есть.

Различие приходит статусом. Замер 22.09.2026: на `Media(id: 999999999)` AniList отвечает **HTTP 404** и телом `{"errors": […], "data": {"Media": null}}`. Тот же 404 приходит, если переменная `id` не передана вовсе — поэтому в запросе она объявлена как `Int!`, чтобы отсечь это на клиенте. Интерцептор в `client.ts` реджектит на `data.errors`, и важно, чтобы статус ответа дожил до вызывающего кода: именно по нему страница выбирает между «такого тайтла нет» и «не достучались».

**Открытый вопрос — мобильная вёрстка.** Баннер выкинуть нельзя, как на главной: здесь он и есть шапка, и на узком экране он помогает узнать тайтл. Высота решена через `clamp`, открытым остаётся расположение шапки.

Замер 02.10.2026, страница тайтла с длинным названием:

| Ширина окна | Колонка заголовка | Строк в названии | Таблица фактов | Описание |
| ----------- | ----------------- | ---------------- | -------------- | -------- |
| 768         | 503               | 2                | 214            | 499      |
| 640         | 390               | 2                | 180            | 420      |
| 480         | 230               | 3                | 154            | 286      |
| 375         | 139               | 5                | 154            | 181      |

Горизонтальной прокрутки нет ни на одной ширине — ломается только читаемость, и перелом приходится между 640 и 480. Виновата не высота баннера, а то, что обложка держит фиксированную ширину и забирает больше половины экрана.

Там же ждёт нижняя граница высоты баннера. Сейчас она задана как `min(20vw, 25vh)` без пола, и на узком экране побеждает `20vw`: замер 05.10.2026 при окне 399 дал баннер в **75 пикселей** — это уже не шапка, а полоска, узнать по ней тайтл нельзя. Побочно слабеет и перекрытие: оно считается долей от высоты, поэтому при 75 обложка заходит на баннер всего на 22 пикселя вместо привычных двух третей. Осмысленный минимум по прежним замерам — 140–175.

Два варианта шапки — бейджи рядом с обложкой и название во всю ширину под ней, либо название рядом с обложкой в узкой колонке — **оба отвергнуты 02.10.2026**, решение не найдено. Там же нужно снять `:wrap="false"` с блока фактов и описания, иначе они делят узкую строку.

**Жанры ведут в поиск.** Тег жанра — ссылка на `/search` с подставленным фильтром, а не просто подпись. Зависит от 5.3: пока поиск заглушка, теги остаются неактивными.

Связанные тайтлы и рекомендации — не в MVP, вынесено в roadmap (11.6).

### 5.5 Мой список `/my-list`

#### Что даёт AniList

У AniList есть две независимые сущности, и путать их нельзя:

| Сущность       | Что это                                      | Мутация              | Чтение                                        |
| -------------- | -------------------------------------------- | -------------------- | --------------------------------------------- |
| **MediaList**  | Полноценный список: статус, прогресс, оценка | `SaveMediaListEntry` | `MediaListCollection(userName:, type: ANIME)` |
| **Favourites** | Отдельное «избранное», просто набор отметок  | `ToggleFavourite`    | `User.favourites`                             |

Нам нужен **MediaList** — он несёт статус и прогресс, а не только факт отметки.

**Запись требует авторизации.** Чтение публичного списка по нику — не требует (на этом строится сравнение списков, 11.4).

#### Два источника списка в MVP

Авторизации в MVP нет (решение зафиксировано, OAuth — 11.3). Вместо неё список собирается из двух слоёв:

**Слой 1 — публичный список AniList по нику, только чтение.** Пользователь указывает свой ник; приложение читает его открытый список. Авторизация не нужна — публичные списки доступны всем.

**Слой 2 — локальные пометки в `localStorage`.** То, что человек отметил в самом приложении. В аккаунт AniList не уезжает.

**Слияние:** оба слоя приводятся к одной форме — объект по `mediaId`. AniList — базовый слой, локальные пометки поверх:

```ts
const merged = { ...fromAniList, ...local };
```

**При конфликте побеждает локальное** — это более свежее явное действие пользователя в этом приложении.

У каждой записи есть признак источника (`'anilist' | 'local'`). Он нужен, чтобы показать в интерфейсе, что пометка локальная и в аккаунт не сохранена, и чтобы «Отключить AniList» убирало только базовый слой, не задевая локальные пометки.

Хранятся слои по-разному: список из AniList — в кеше с TTL, его всегда можно перезапросить; локальные пометки — в `localStorage`, это единственная копия.

#### Где указывается ник

**Каноническое место — этот экран.** Сверху блок подключения: поле ввода и кнопка «Загрузить». После подключения — строка «Список AniList: `ник`» и кнопка «Отключить».

**Расписание** своей формы ввода не имеет. Если включён фильтр «только мой список», а ника нет и локальных пометок тоже нет — подсказка «Укажи ник AniList или отметь тайтлы вручную» со ссылкой сюда.

**Главная** тоже своей формы не имеет: там плашка-приглашение с кнопкой «Указать ник», ведущей сюда (5.1). Плашка закрывается навсегда, и это безопасно именно потому, что канонический вход — пункт меню «Мой список», а не она.

**Источник истины для отображения — URL, `localStorage` помнит выбор по умолчанию.** Согласуется с тем же принципом для фильтров поиска (5.3):

```
/schedule?user=ник
```

- есть `user` в URL — показываем список этого пользователя (так работает шаринг ссылки);
- нет — берём сохранённый ник из `localStorage`;
- ник из URL сохранённый **не перетирает**: посмотрел чужое расписание, вернулся — своё на месте.

Тот же механизм переиспользуется сравнением списков (11.4).

#### Чтение списка по нику

```graphql
query UserList($userName: String) {
  MediaListCollection(userName: $userName, type: ANIME) {
    lists {
      entries {
        mediaId
        status
        progress
        score
      }
    }
  }
}
```

`MediaListCollection` отдаёт записи разбитыми по пользовательским категориям — их нужно схлопнуть в один плоский набор.

**Два разных сценария ошибки, сообщения должны различаться:**

- ника не существует — AniList вернёт ошибку → «Пользователь не найден»;
- список закрыт настройками приватности — придёт пусто → «Список закрыт настройками приватности». Если показать здесь «список пуст», человек решит, что приложение сломано.

#### Формат хранения

**Ключевое решение: статусы хранятся под теми же именами, что у AniList** — значения перечисления `MediaListStatus`:

```
CURRENT · PLANNING · COMPLETED · DROPPED · PAUSED · REPEATING
```

Русские подписи («смотрю», «запланировано», …) живут только в файлах локализации. Смысл двойной: данные из AniList ложатся в ту же модель без преобразования, а при переходе на OAuth (11.3) меняется источник данных, а не модель — не придётся мигрировать сохранённые записи и переписывать компоненты.

**Форма записи локального слоя в `localStorage`:**

```ts
{
  version: 1,
  items: {
    [mediaId: number]: {
      status: MediaListStatus
      progress: number
      score?: number
      updatedAt: number
    }
  }
}
```

**Объект по `mediaId`, не массив** — это важно не только для этого экрана. Расписание на каждой карточке эпизода решает, помечать её как «в моём списке» или нет; при массиве это перебор на каждую карточку, при объекте — обращение по ключу.

**Синхронизация:** `watch` на стор с `{ deep: true }` → `localStorage.setItem`. Чтение — при инициализации стора.

**Данные из `localStorage` — недоверенный ввод.** Пользователь мог их испортить руками, а формат мог поменяться между версиями приложения. Парсинг обёрнут в `try/catch` плюс проверка формы объекта и поля `version`; при несовпадении — сброс к пустому списку, а не падение приложения.

#### Экран

Группировка по статусам (вкладки или секции). Для каждого тайтла — прогресс по эпизодам.

**Состояния:** пустой список с приглашением перейти в каталог.

### 5.6 404

Иллюстрация/логотип, текст, кнопка на главную.

## 6. Работа с API

### 6.1 Клиент

Axios-инстанс на `https://graphql.anilist.co`, POST-запросы вида `{ query, variables }`. Интерсептор ответа: проверка `data.errors` (GraphQL отдаёт HTTP 200 даже при ошибке — это отдельная ловушка), приведение к единому виду ошибки.

**Клиент ошибки не показывает (решено 30.08.2026).** Он отклоняет промис и отдаёт отказ наверх как есть — показывает тот, кто знает контекст. Всплывашка из интерсептора убрана вместе с `createDiscreteApi`: она мешала фоновому обновлению быть тихим (6.4) и не знала про тему приложения, поэтому в тёмной теме выходила светлой плашкой. Внутри приложения эту роль играет `useMessage()`, у него такой проблемы нет.

Сейчас всплывашки нет нигде: у расписания своё пустое состояние с кнопкой повтора, на главной ошибка не показывается вовсе — записано в долге.

**Открытый вопрос:** пустое состояние говорит «данные потеряны» при любой ошибке, поэтому при `429` человек будет жать «Повторить» и получать тот же отказ. Причина отказа должна жить в постоянном состоянии, а не во временной всплывашке. Отложено.

### Лимит запросов — справка

**Решение по обработке отложено.** Ниже только собранные факты, чтобы не выяснять их заново. Реализация — когда до неё дойдут руки.

**Лимит — 30 запросов в минуту.** Документация заявляет 90, но тут же оговаривает, что API «в деградированном состоянии» и ограничен 30. Замер 16.08.2026 подтверждает: `x-ratelimit-limit: 30`. Таймаут после превышения — одна минута. Тело ошибки: `{"message": "Too Many Requests.", "status": 429}`.

**Заголовки по документации:** `X-RateLimit-Limit` и `X-RateLimit-Remaining` приходят всегда; `Retry-After` (секунды) и `X-RateLimit-Reset` (unix-таймстемп) — только при 429.

**Браузеру видно не всё.** Замеренный читаемый набор на успешном ответе: `cache-control`, `content-type`, `x-ratelimit-limit`, `x-ratelimit-remaining`. Первые два открыты спецификацией, значит AniList явно выставляет наружу только два своих — `Retry-After` и `X-RateLimit-Reset` через `Access-Control-Expose-Headers` не открыты.

**Два разных вида отказа.** Обычно приходит честный `429`, доступный как `error.response.status`. При резком всплеске запросов ответ приходит вообще без CORS-заголовков, и до скрипта не доходит: `error.response` отсутствует, `error.code` равен `ERR_NETWORK`, причина неотличима от отсутствия сети.

**Насколько это вообще актуально.** При работающем кеше недель обычный сценарий использования в лимит не упирается — 30 запросов в минуту набираются только целенаправленным перебором. В упомянутом замере лимит был выбит диагностикой, а не обычным пользованием.

**403 без заголовка `Referer` (10.09.2026).** На время своих проблем со стабильностью AniList начал отвечать `403` с текстом «The AniList API has been temporarily disabled» на запросы без `Referer`. Замерено: `User-Agent` и `Origin` не помогают, любой `Referer` — включая `http://localhost:5173/` и `https://example.com/` — даёт `200`. Похоже на грубый фильтр ботов, а не на проверку домена.

Приложения это не касается: браузер подставляет `Referer` сам, исходя из адреса страницы. А вот **кодогенерация ходит за схемой из Node**, без браузера, и потому упиралась в отказ — отсюда заголовок в `codegen.ts`. Значение там любое и от адреса развёртывания не зависит: `codegen` выполняется на машине разработчика, а не на сервере.

### 6.2 Адреса в бою идут через переписывание на Vercel

**Решено 22.09.2026, после выкладки.** Из России `s4.anilist.co` недоступен — картинки не грузились вовсе. Запросы к `graphql.anilist.co` формально проходили, но часть висела без ответа и обрывалась по таймауту клиента. Для портфолио это смертельно: ревьюер открывает ссылку и видит пустоту.

Решение — **переписывание путей на стороне хостинга, без серверного кода.** В `vercel.json`:

| Путь в приложении | Куда уходит                    |
| ----------------- | ------------------------------ |
| `/img/:path*`     | `https://s4.anilist.co/:path*` |
| `/api/anilist`    | `https://graphql.anilist.co`   |

Браузер обращается только к собственному домену приложения, а за границу ходит уже машина Vercel. Открытым прокси это не становится: адрес назначения зашит в правило, произвольный хост через него не запросить.

**В разработке прокси не используется — и это принципиально.** Прокси для dev-сервера крутился бы на локальной машине, то есть последний участок пути упирался бы в ту же блокировку, только с лишним звеном: картинки грузятся медленно, запросы падают. Поэтому и в `client.ts`, и в `proxyImageUrl` стоит проверка `import.meta.env.PROD`, а в `vite.config.ts` никакого `server.proxy` нет.

Следствие, о котором надо помнить: **путь через прокси не проверяется локально.** Ошибка в `vercel.json` видна только после выкладки. Смягчается тем, что каждая ветка на Vercel получает свой временный адрес, так что проверять правила можно, не трогая боевой.

Кодогенерации это не касается: она работает из Node и ходит к AniList напрямую, со своим заголовком `Referer` (раздел 2).

### 6.3 Запрос расписания

```graphql
query Schedule($start: Int, $end: Int, $page: Int) {
  Page(page: $page, perPage: 50) {
    pageInfo {
      hasNextPage
    }
    airingSchedules(
      airingAt_greater: $start
      airingAt_lesser: $end
      sort: TIME
    ) {
      airingAt
      episode
      media {
        id
        title {
          romaji
          english
        }
        coverImage {
          medium
          color
        }
      }
    }
  }
}
```

`perPage` у AniList максимум 50, а неделя релизов бывает больше сотни → **обязателен цикл по `hasNextPage`**, не один запрос.

**Плотность данных падает с удалением в будущее.** Замерено 10.08.2026:

| Неделя     | Записей | Ещё страницы |
| ---------- | ------- | ------------ |
| текущая    | 50      | да           |
| +5 недель  | 50      | да           |
| +13 недель | 38      | нет          |
| +22 недели | 15      | нет          |

Вещатели публикуют сетку на сезон вперёд, поэтому далёкие недели законно возвращают мало записей, а совсем далёкие — ноль. Это не ошибка загрузки, и интерфейс должен отличать «неделя загружена и пуста» от «неделя не загружена».

**`total` и `lastPage` доверять нельзя.** У ближних недель API отдаёт `total: 5000` и `lastPage: 100` — это потолок выдачи, а не настоящее количество. Признак конца — только `hasNextPage`.

### 6.4 Кеширование

| Данные            | TTL           | Где                                            |
| ----------------- | ------------- | ---------------------------------------------- |
| Расписание недели | 15 мин        | Pinia, `Map<weekKey, { data, fetchedAt }>`     |
| Популярное / топ  | 1 час         | Pinia                                          |
| Детали тайтла     | 1 час         | Pinia, `Map<id, …>`                            |
| Результаты поиска | не кешируются | последняя выдача держится в сторе для возврата |

Прошлые недели можно кешировать бессрочно — они уже не изменятся. То есть TTL применяется не ко всем записям, а только к неделям, которые ещё не закончились.

Кеш живёт в памяти на время сессии. Персист в `localStorage` — в roadmap, не в MVP.

#### Как устроено обновление (решено 30.08.2026)

Запись недели хранит время **успешной** загрузки. Дальше два независимых вопроса: протухлость решает, идти ли в сеть, а наличие данных — шумно или тихо. Путать их нельзя: запись, упавшая на первой загрузке, протухшая, но за ней пустой экран, и обновлять её надо шумно.

- **Шумно** (показывать нечего): скелетон, при отказе состояние ошибки с кнопкой повтора.
- **Тихо** (данные есть, но устарели): старое остаётся на экране, запрос идёт фоном, замена по факту успеха. Приём известен как stale-while-revalidate.

**Отказ фонового обновления пользователю не показывается** — он его не запускал. Ошибка пишется в состояние только в шумной ветке и снимается по успеху. Время успешной загрузки при отказе не двигается, поэтому данные остаются протухшими и повтор случится сам при следующем обращении.

**Пометка возраста данных** вместо сообщения об отказе: «не удалось обновить» — событие, оно исчезает; «данные от 14:20» — состояние, верное всё время. Открыто: где ей место и показывать ли всегда или только после TTL. Смысл она приобретёт вместе с персистом.

Из пометки следует и второе требование: увидев возраст, человек захочет обновить данные сам — он не знает, когда это случится само. Значит пометка не может быть просто надписью, ей нужна либо кнопка обновления рядом, либо сообщение о том, когда произойдёт следующая попытка. Иначе она сообщает о проблеме и не даёт с ней ничего сделать.

**Пауза после `429`** — отложена. Ждать стоит только когда сервер сам сказал ждать; для этого понадобится код ошибки и отдельное время последней попытки. При работающем кеше обычное пользование в лимит не упирается (см. справку о лимите).

**Ревалидация открытой страницы отложена.** Единственный триггер проверки — переключение недели. Обновление через `visibilitychange` вернётся, когда появится причина: переносы уже объявленных релизов редки.

### 6.5 Отмена запросов и гонки

**Решено 02.10.2026.** Две ситуации, где ответ приходит, когда он уже не нужен: быстрые переходы между тайтлами и набор в поиске. Без защиты поздний ответ по прошлому запросу перезаписывает данные текущего.

**Запрос обрывается, а не просто игнорируется.** `AbortController`, его `signal` уходит третьим аргументом в `graphqlRequest` — конфиг там уже принимается, менять helper не нужно. Причина выбрать обрыв, а не сверку на выходе: у AniList есть ограничение по частоте, а при таймауте в 10 секунд брошенный запрос ещё и держит соединение.

**Одной отмены мало — нужна проверка актуальности.** Отменённый запрос попадает в `catch`, выходит по `return`, но **`finally` выполняется и после `return`**. Без проверки он погасит загрузку уже другого, живого запроса. Поэтому и в `finally`, и в успешной ветке стоит вопрос «этот контроллер ещё текущий?», и только при утвердительном ответе трогается состояние.

Сравниваются сами объекты контроллеров, а не идентификаторы: так работает и повторное открытие того же тайтла.

**Отмена не должна попадать под задержку ввода.** В поиске обрыв вызывается в необёрнутом обработчике, а отложен только сам запрос. Если отменять внутри отложенной функции, обрыв опаздывает на 500 мс — дольше, чем идёт запрос, и отменять оказывается нечего. Замер 02.10.2026: выдача по стёртой строке висела на экране почти секунду.

**`ERR_CANCELED` отсекается первой строкой `catch`**, иначе каждый быстрый переход показывает экран ошибки.

#### Композабл `useAbortController`

Общий для стора карточки и поиска, отдаёт три функции: создать контроллер (обрывая прежний), проверить актуальность, сбросить.

| Что отменяет                            | Чем закрывается                                             |
| --------------------------------------- | ----------------------------------------------------------- |
| предыдущий запрос при новом             | создание контроллера обрывает прежний                       |
| запрос при уходе со страницы тайтла     | обрыв в наблюдателе маршрута, при `params.id === undefined` |
| запрос при коротком вводе в поиске      | обрыв в обработчике ввода                                   |
| запрос при уничтожении области эффектов | `onScopeDispose` внутри композабла                          |

Последняя строка — страховка, а не работающий механизм: **область эффектов setup-стора Pinia привязана к экземпляру Pinia, а не к компоненту.** Уход со страницы стор не уничтожает, `onScopeDispose` там сработает только при закрытии вкладки. `SearchAutocomplete` тоже живёт всё время, он внутри шапки. Поэтому обрыв в наблюдателе маршрута обязателен и отдельно — заменить его на `onScopeDispose` нельзя.

## 7. Работа со временем — правила

Это самое ошибкоопасное место проекта. Правила обязательны к соблюдению.

1. **`airingAt` от AniList — unix-секунды в UTC.** Это абсолютный момент времени, одинаковый для всех на планете.
2. **Хранить и передавать — в unix/UTC. Форматировать — в самый последний момент, в компоненте.** Никаких «уже отформатированных» дат в сторе.
3. **Группировка по дням выполняется в локальной зоне пользователя**, а не в UTC и не в JST. `dayjs.unix(airingAt).format('YYYY-MM-DD')` даёт локальную дату — это и есть ключ группы.
4. **Не склеивать и не парсить даты строками вручную.** Никаких `new Date('2026-07-30')` — такая строка парсится как UTC-полночь, а не локальная.
5. **Для арифметики использовать календарные единицы, не часы.** `dayjs().add(1, 'day')` учитывает переход на летнее время, `add(24, 'hour')` — нет.
6. **Границы недели** — через плагин `isoWeek` (неделя с понедельника). Обычный `startOf('week')` зависит от локали и в en-US даёт воскресенье.
7. **Один тикер на всё приложение.** Обратные отсчёты не заводят по `setInterval` на карточку. В сторе один интервал (раз в 30 сек), обновляющий реактивный `now`; карточки вычисляют разницу от него. Интервал очищается при размонтировании.
8. **Таймзона пользователя** определяется как `Intl.DateTimeFormat().resolvedOptions().timeZone`. **Язык интерфейса** — отдельная сущность, из `navigator.language` или выбора пользователя. Одно не выводится из другого.
9. `dayjs.locale('ru' | 'en')` переключается синхронно с языком vue-i18n.

## 11. Roadmap — после MVP

Порядок отражает соотношение «польза для портфолио / трудозатраты».

### 11.1 Тесты (Vitest + Vue Testing Library)

Первая цель — чистые функции: группировка расписания по дням, вычисление границ недели, форматирование обратного отсчёта, парсинг и валидация фильтров из URL. Это функции без DOM и без сети, тестировать их проще всего, а покрывают они самую ошибкоопасную логику.

Вторая цель — сторы Pinia (кеш, TTL) и пара компонентов.

Цель не в проценте покрытия, а в наличии осмысленных тестов.

**Обязательное условие для тестов на даты.** Плагины dayjs подключаются в `main.ts` (`dayjs.extend(isoWeek)` и др.). В тестовом запуске `main.ts` не выполняется, поэтому в конфиг Vitest нужен `setupFiles`, повторяющий те же `extend`. Без него `startOf('isoWeek')` молча вернёт неизменённую дату — dayjs не распознаёт неизвестную единицу и не выдаёт ошибку, так что тест упадёт с сообщением, уводящим в сторону от настоящей причины.

### 11.2 CI на GitHub Actions

Один workflow, запускается на каждый push и pull request: установка зависимостей → lint → `vue-tsc` → тесты → сборка. Бейдж статуса в README.

### 11.3 OAuth AniList

**Нужен только для записи.** Чтение списка в MVP уже решено ником без авторизации (5.5), так что OAuth добавляет ровно одну возможность: отмечать статус и прогресс так, чтобы это сохранялось в аккаунте AniList (мутация `SaveMediaListEntry`), а не только локально.

Стор личного списка уже спроектирован под слияние источников, поэтому OAuth добавляет третий слой, а не переписывает модель. `localStorage` и чтение по нику остаются режимами для незалогиненных.

Может остаться неcделанным навсегда — ценность фичи невелика по сравнению со сложностью (два режима интерфейса, обработка истёкшего токена, совпадение redirect URI между localhost и продакшеном).

**Бэкенд не нужен.** AniList поддерживает implicit grant: после редиректа токен приходит прямо во фрагменте URL, обменивать его на сервере не требуется. То есть авторизация реализуема в чистом SPA и не противоречит разделу 12.

Осознанный компромисс: implicit grant отдаёт долгоживущий токен (у AniList — год), который хранится на клиенте. Для пет-проекта приемлемо, для продакшена потребовался бы authorization code flow с серверной частью.

### 11.4 Сравнение списков

Экран `/compare?a=ник1&b=ник2`: что смотрели оба, что смотрел только один, расхождение оценок. Работает по публичным никам, без авторизации — демонстрируется за 20 секунд. Заодно оправдывает всю работу с состоянием в URL.

### 11.5 PWA — TODO, отложено

**Статус: отложено осознанно.** Решение не принято, потому что польза для этого проекта пока неочевидна. Вернуться к вопросу, когда появится один из поводов:

Что это даст технически: `vite-plugin-pwa` генерирует манифест, иконки и service worker. Приложение устанавливается на телефон, расписание доступно офлайн из кеша. Push-уведомления «серия вышла» требуют серверной части и в рамках фронтенд-проекта не делаются.
